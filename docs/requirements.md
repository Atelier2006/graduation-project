## 1. 概要

### 1.1 背景

- フィッシングの報告件数は2024年に171万8,036件で過去最多になった。2026年7月の報告では、なりすまされたブランドが101件にのぼる。
- 特殊詐欺とSNS型投資・ロマンス詐欺の被害額は、2025年に合計3,257.4億円で過去最悪になった（警察庁の確定値）。警察官をかたる「ニセ警察詐欺」が急増し、SNS型投資詐欺の入口は広告が最も多い。
- **被害は高齢者だけのものではない。** 2025年の特殊詐欺では20代・30代の認知件数が前年の2倍以上に増えた。ニセ警察詐欺の被害者は30代が最も多く、SNS型投資詐欺は50代、SNS型ロマンス詐欺は40代〜60代が全体の75.6%を占める（警察庁の確定値。[被害データの初期値](../seed/victim_stats.yaml)）。
- 偽のセキュリティ警告で電話をかけさせる「サポート詐欺」の相談は、2026年4〜6月にIPAの相談窓口で1,428件あり、相談全体の37.3%を占めた。
- 差出人欄に実在するサービスのドメインを使ったものが、2026年7月に調査用アドレスに届いたフィッシングメールの約26.5%を占めた。**見た目だけでは見抜けない詐欺が増えている**ため、見抜くポイントを知るだけでなく、「迷ったらメッセージのリンクを使わず、公式アプリやブックマークから確かめる」行動を、**実際の操作として**身につけることが大切になる。
- 詐欺は1回の判断で終わらない。メッセージを開く、リンクを押す、入力する、電話で話す、と**何度も引き返すチャンスがある**。問題文を読んで選択肢を1つ選ぶ形式では、この「途中で気づいて引き返す」練習ができない。

### 1.2 目的

1. **手口を知り、見抜くポイントを身につける。**
2. **迷ったときの正しい行動を、操作として体験する**（リンクを開かない、公式から確かめる、電話を切る、相談する）。途中で間違えても、引き返す方法と、被害にあったあとの対処を知る。
3. **自分の選択を、ほかの人や実際の被害のデータと比べて考える**（どこで多くの人が危ない方へ進むのか、実際にはどんな人が被害にあっているのか）。
4. **家族や周りの人と一緒に学ぶ**（挑戦状で同じシナリオを遊び、誰がどの結末になったかを見比べる）。

### 1.3 コンセプト

> 本物そっくりに動く架空のメールアプリ・メッセージアプリ・ブラウザを自分で操作し、また電話や対面での口頭のやり取りをチャットで体験して、「どう対処するか」を自分で見つける。選んだ行動で物語が分かれ、結末が変わる。
> 終わったあとは、ゲーム『Detroit: Become Human』の章の終わりのように、**分岐のフローチャートで、自分の通った道と、ほかの人がどの選択肢を選び、どの結末になったかを見られる。**
> さらに、公的機関の統計から**「実際には、どんな人が被害にあっているのか」**を示し、アプリの中で集まった行動のデータと並べて見せる。

### 1.4 3階層

| 第1階層：ユーザー価値 | 第2階層：技術要素 | 第3階層：対象分野 |
| --- | --- | --- |
| **安全**（＋学べる・楽しい） | **データ分析・データの可視化**（＋WebAPI開発） | **地域社会**（＋学生生活） |

データ分析・可視化は、次の3つで前面に出す。

| 何を見せるか | データ | 機能 |
| --- | --- | --- |
| みんなはどこで、どの選択をしたか | アプリの中の操作の記録 | 分岐のフローチャート（[F-19](#f-19-分岐のフローチャート)） |
| どんな人が、どこで引っかかるか | アプリの中の操作の記録（年代別・調べたかどうか別） | 統計（[F-13](#f-13-統計分析)） |
| 実際には、どんな人が被害にあっているか | 公的機関の統計（出典付き） | 実際の被害データ（[F-20](#f-20-実際の被害データ)） |

### 1.5 成功指標

| 指標 | 目標 | 測り方 |
| --- | --- | --- |
| 学習効果 | 同じ手口のシナリオで「安全」以上の結末にたどり着いた割合が、1本目より2本目以降で15ポイント以上上がる | アプリの記録（[F-13](#f-13-統計分析)） |
| 確かめる行動 | 「差出人を確かめる」「公式アプリで確かめる」などの確かめる操作をした割合が、1本目より上がる | アプリの記録 |
| 使いやすさ | SUS 68点以上（目標75点） | 完成後のアンケート |
| 展示会 | 2日間で100人以上が体験する | 展示会モードの記録 |

## 3. 範囲（スコープ）

### 3.1 必須（MVP）

- アカウント（登録・ログイン・ログアウト・パスワード変更・退会）
- **分岐型のシナリオ**
  - アプリ型：仮想のメールアプリ・メッセージアプリ（SMS・SNSのDM）・ブラウザと、仮想のホーム画面を操作して進む
  - 会話型：電話や対面での口頭のやり取りを、チャット形式で進む
  - 「調べる」操作（情報を見る）と「決める」操作（物語が進む）。決める場面が1本に2〜4回あり、途中で引き返せる
  - 結末（最善・安全・危ない・被害の4段階）と、結末ごとの解説・被害にあったあとの対処
- **振り返りと分岐のフローチャート**（自分の道筋、みんなが選んだ割合、結末の割合、年代別の絞り込み）
- **実際の被害データ**（公的機関の統計を出典付きでグラフにし、アプリの中のデータと並べる）
- 人とシナリオのレーティング、難易度の表示、苦手な手口を多めに出す「おまかせ」
- 履歴・苦手分析・お気に入り・マイページ
- ランキング、コメント
- 統計（手口別・形式別の「被害の結末になった率」、落とし穴になった選択肢、調べた人と調べなかった人の比較、年代別）
- シナリオの作成（YAMLで書いて取り込む）・確認・公開の流れ（編集者向け）
- 相談先の案内、利用規約、プライバシーポリシー
- 初期のシナリオ12本（[問題集](question-bank/README.md)の事例と問題案を素材にして書く）

### 3.2 追加

- 展示会モード（大画面に当日のフローチャートを表示、1本だけ遊ぶ短縮版）
- 挑戦状（家族や友達が同じシナリオを遊び、誰がどの結末になったかをフローチャートで見比べる）
- 結末の一覧（見つけた結末を集める）と、行ったことがある場面からのやり直し
- 困ったときのヒント
- 怪しいメッセージの投稿と審査
- URLの読み方トレーニング
- 文字を大きくする切り替え、会話の時間差表示をやめる切り替え
- フォームでのシナリオの編集
- シナリオを24本に増やす

### 3.3 余裕があれば

- 手口図鑑（手口ごとの解説ページ）
- 急がせる演出（会話型で、返事までの時間に制限を付ける）
- 学習の連続日数の表示、バッジ
- 主催者向けのCSV出力

### 3.4 対象外（作らない）

| 内容 | 理由 |
| --- | --- |
| 実際に届いたメッセージや実在のURLが安全かどうかの判定 | 判定を誤ると利用者に実害が出る。外部のサービスも必要になる |
| 生成AIによるシナリオの作成や、自由入力の会話 | 内容の正確さを保証しにくい。今回は人が作って確認する。会話型の返事は選択肢から選ぶ |
| 電話の音声の再現 | 文章（チャット形式）で再現する |
| 長い物語（1本で10分以上） | 1本は3〜5分で終わる長さにする。分岐が増えすぎると作成と確認が間に合わない |
| 被害データの自動取得 | 外部のサイトから自動で取らない。管理者が出典を確かめて手で登録する |
| メールの送信（パスワード再設定メールなど） | 外部のメールサービスが必要になる。パスワードを忘れたら管理者が再設定する |
| スマホのネイティブアプリ、多言語対応 | Webのレスポンシブ表示で対応する |

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| シナリオ | 1つの詐欺（または本物の連絡）の体験。場面・操作・結末のセット。1本3〜5分 |
| 形式 | シナリオの進め方。アプリ型（メール・メッセージ・ブラウザ）と会話型 |
| 場面 | シナリオの中の1つの画面の状態（例：受信トレイ、メールを開いた画面、偽のログイン画面、電話で相手が話している場面） |
| 調べる操作 | 物語を進めずに情報を見る操作（差出人の詳細を開く、リンクを長押ししてURLを見る、など）。何度でもできる |
| 決める操作 | 物語が次の場面か結末に進む操作（リンクを押す、入力する、電話を切る、公式アプリを開く、など） |
| 気づき | 調べる操作で見つかる、見抜く手がかり（例：差出人のドメインが公式と違う） |
| 結末 | シナリオの終わり方。最善・安全・危ない・被害の4段階で評価する（[5.3節](#53-結末の評価)） |
| 道筋 | 1回のプレイで通った場面と、選んだ操作の順番 |
| フローチャート | シナリオの全体の分岐を図にしたもの。自分の道筋と、みんなが選んだ割合を重ねて表示する |
| 1本目の記録 | ある人があるシナリオを初めて遊んだときの記録。フローチャートの割合はこれで計算する |
| おまかせ | 3本のシナリオを自動で選んで続けて遊ぶモード |
| レート | 利用者の見抜く力を表す数値 |
| 難易度 | シナリオの難しさを表す数値。プレイが集まるほど正確になる |
| 挑戦状 | 会員が固定したシナリオのセットと、それで遊ぶためのURL・QRコード |
| 架空ブランド | シナリオ用に作った、実在しない会社・サービス |
| 登録ドメイン | URLのうち、その持ち主を表す部分（例：`login.kotori-bank.example` の `kotori-bank.example`） |
| 詐欺の種類 | 公的機関の統計の区分（特殊詐欺、ニセ警察詐欺、SNS型投資詐欺、SNS型ロマンス詐欺など）。シナリオと被害データを結び付ける |
| 被害データ | 公的機関の統計から登録した、実際の被害の件数・構成など。必ず出典を付ける |

## 5. シナリオ（コンテンツ）の要件

このサービスの価値はシナリオの質で決まる。シナリオは人（チーム）が Claude と一緒に作り、別の人が確認してから公開する。

### 5.1 形式

**アプリ型**：仮想のスマホの中で、本物らしく動くアプリを操作する。選択肢を文章で並べず、**アプリの画面の中のボタン・メニュー・長押しとして置く**。対処法は、利用者が画面の中から自分で見つける。

| 形式 | 再現するアプリ | 主な操作（調べる／決める） | 主な手口の例 |
| --- | --- | --- | --- |
| メール | メールアプリ（受信トレイ、メール本文、差出人の詳細、迷惑メールとして報告、削除、返信） | 調べる：差出人の詳細、リンクの長押し（URL表示）。決める：リンクを押す、返信する、報告する、削除する | カード会社・通販・証券会社のなりすまし |
| メッセージ | SMS、SNSのダイレクトメッセージ | 調べる：送信元の番号・アカウントの詳細、リンクの長押し。決める：リンクを押す、返信する、ブロック・報告する | 宅配の不在通知、料金の未払い、投資グループへの勧誘、高額バイト |
| ブラウザ | アドレスバーとページ（偽のログイン画面、偽の通販サイト、偽のセキュリティ警告） | 調べる：アドレスバー、会社概要のページ。決める：入力して送信する、電話をかける、タブを閉じる | 偽のログイン画面、偽の通販サイト、サポート詐欺 |

アプリ型のシナリオでは、どの場面からでも**仮想のホーム画面**に戻れる。ホーム画面には、架空ブランドの公式アプリ、ブックマーク付きのブラウザ、電話（家族・相談窓口・架空ブランドの公式窓口）、家族とのチャットを置く。「公式から確かめる」「家族に相談する」は、ここから自分で見つける。

**会話型**：電話・対面・ビデオ通話での口頭のやり取りを、チャット形式で再現する。相手の発言が順に表示され、利用者は返事や行動を2〜4個の選択肢から選ぶ。電話の場面では「電話を切る」、どの場面でも「家族に相談する」を常に選べる。

| 再現する場面 | 主な手口の例 |
| --- | --- |
| 電話（固定電話・携帯電話） | ニセ警察詐欺、オレオレ詐欺、還付金詐欺、サポート詐欺の電話 |
| ビデオ通話 | 警察官を装ってビデオ通話に誘う手口 |
| 対面（自宅への訪問など） | キャッシュカードの受け取りに来る手口 |
| SNSでの長いやり取り | ロマンス詐欺、投資グループでの勧誘 |

### 5.2 シナリオの組み立て

| 項目 | 決まり |
| --- | --- |
| 長さ | 1本3〜5分。決める場面（分岐点）は2〜4個。結末は3〜5個 |
| 一回選んで終わりにしない | 危ない操作をしても、すぐに結末にしない。次の場面で**引き返すチャンス**を置く（例：偽のログイン画面で、入力する前にアドレスバーを確かめて閉じる） |
| 調べる操作 | 各場面に1〜4個。見抜く手がかりになるもの（気づき）を1つ以上入れる。気づきを見なくても進めるが、見た気づきは振り返りで「見つけた気づき」として数える |
| 詐欺と本物 | 本物の連絡のシナリオも入れる（詐欺7：本物3を目安）。本物では、公式から確かめて手続きを終えるのが最善で、本物を無視して困る結末（例：本物の配達を受け取れない）も置く |
| 分岐の形 | 同じ場面に戻る輪（ループ）を作らない。すべての場面からいずれかの結末にたどり着ける。たどり着けない場面を作らない（[10.7節](#107-シナリオの検証)で自動チェック） |
| 被害の結末のあと | 被害にあったあとの正しい対処（カード会社に連絡する、パスワードを変える、警察や消費者ホットラインに相談する）を必ず示す |

**例：宅配の不在通知のSMS（架空ブランド「ハシレ運輸」、詐欺）**

```mermaid
flowchart TD
    s1["場面1：SMSが届く<br>調べる：送信元の番号／リンクを長押し"]
    s1 -->|"リンクを押す"| s2["場面2：再配達のページ（ブラウザ）<br>調べる：アドレスバー"]
    s1 -->|"ホーム画面から公式アプリを開く"| s4["場面3：公式アプリ<br>配達の予定がない"]
    s1 -->|"削除する"| eB1(["結末：安全<br>被害なし。報告すればもっとよかった"])
    s2 -->|"名前と電話番号を入力する"| s3["場面4：カード番号の入力画面"]
    s2 -->|"タブを閉じる"| eB2(["結末：安全<br>入力せずに引き返せた"])
    s3 -->|"カード番号を入力する"| eD(["結末：被害<br>カードが不正に使われる → カード会社へ連絡"])
    s3 -->|"おかしいと思ってやめる"| eC(["結末：危ない<br>電話番号を渡した → 迷惑な連絡に注意"])
    s4 -->|"迷惑メッセージとして報告して削除"| eA(["結末：最善<br>公式で確かめ、報告まで"])
```

### 5.3 結末の評価

| 評価 | 意味 | 点数（[10.1節](#101-レーティング)） |
| --- | --- | --- |
| 最善 | 被害なし。公式から確かめる・相談する・報告するなど、勧められる行動まで取った | 1.0 |
| 安全 | 被害なし。ただし確かめずに無視した、本物を無視して手続きできなかった、など | 0.7 |
| 危ない | 被害の一歩手前。個人情報の一部を渡した、途中まで手続きした | 0.3 |
| 被害 | だまされた（お金・カード情報・アカウントを取られた） | 0 |

### 5.4 手口の分類（タグ）

| コード | 手口 | 内容 |
| --- | --- | --- |
| T01 | なりすまし | 企業・サービス・公的機関の名前をかたる |
| T02 | そっくりドメイン | つづり違い、紛らわしい文字（l と 1 など）、別の文字体系の文字を使う。公式の名前に単語を足したもの（`kotori-bank-login.example` など）も含む |
| T03 | URLの見せかけ | 短縮URL、正規の名前をサブドメインに入れる、表示と飛び先が違う |
| T04 | 急がせる・不安をあおる | 「アカウント停止」「本日中に」「逮捕状が出ている」 |
| T05 | 利益で釣る | 当選、高額報酬、「必ずもうかる」 |
| T06 | 情報を入力させる | ID・パスワード、カード番号、ワンタイムパスワード |
| T07 | お金を払わせる | 電子マネーのカード番号を伝えさせる、暗号資産、個人名義の口座への振込 |
| T08 | 電話をかけさせる | 偽の警告画面に出るサポートの番号、「至急連絡を」 |
| T09 | 不在通知 | 宅配業者をかたる再配達の案内 |
| T10 | 偽のセキュリティ警告 | 警告音・全画面表示で慌てさせるサポート詐欺 |
| T11 | 投資・副業の勧誘 | SNS広告、著名人の名前、投資グループへの招待 |
| T12 | 親しくなってから | 恋愛感情や信頼関係を作ってから、投資やお金の話をする |
| T13 | 警察・公的機関をかたる | ニセ警察詐欺、税金・公共料金の未納 |
| T14 | 闇バイトの勧誘 | 「高額・即日」「荷物を受け取るだけ」 |
| T15 | 偽の通販サイト | 極端な値引き、不自然な日本語、個人名義の振込先 |

本物のシナリオには手口のタグを付けず、「本物と確かめる方法」を解説に書く。シナリオには、被害データと結び付けるための**詐欺の種類**（ニセ警察詐欺、SNS型投資詐欺など）も付ける。公的な統計がない種類（フィッシングの一部など）は付けなくてよい。

### 5.5 本数と配分

| 項目 | MVP | 最終 |
| --- | --- | --- |
| 本数 | 12本 | 24本 |
| 形式 | メール3、メッセージ3、ブラウザ2、会話型4 | 各形式5本以上 |
| 詐欺と本物 | およそ7：3 | 同じ |
| 手口 | 主な手口（T01・T04・T06・T09・T10・T11・T13）を1本以上 | すべての手口を1本以上 |
| 被害データと結び付くシナリオ | 4本以上（ニセ警察詐欺、SNS型投資詐欺、SNS型ロマンス詐欺、特殊詐欺のいずれか） | 8本以上 |
| 初期の難易度 | やさしい・ふつう・むずかしいを作成者が設定（プレイが集まると自動で更新される） | 同じ |

[問題集](question-bank/README.md)の事例（出典を開いて確かめた128件）と問題案（92問）を素材にする。問題案のメッセージ・見るべき場所・最善の行動を、シナリオの最初の場面・調べる操作・最善の結末に書き直す。

### 5.6 作成のルール（必ず守る）

| ID | ルール |
| --- | --- |
| C-01 | **実在の企業名・サービス名・ロゴ・人名を使わない。** 架空ブランドを作って使う（例：コトリ銀行、ハシレ運輸、ポチッと通販。一覧は [seed/brands.yaml](../seed/brands.yaml)）。架空ブランドの名前は、実在しないことをWeb検索で確かめる。被害データの区分名（出典のとおりの名前）はこのルールの対象外 |
| C-02 | **URLは予約済みのドメインを使う。** 例示用に予約されている `.example` や `.test` を基本とする（例：`kotori-bank.example`）。シナリオの中のURLはリンクにせず、押しても外部のサイトに移動しない |
| C-03 | **電話番号は一部を伏せる。** 例：`010-XXXX-XXXX`。相談窓口（#9110、188）は本物の番号を書くが、仮想の電話では実際に発信しない |
| C-04 | **実際の詐欺メッセージの画面写真をそのまま使わない。** 公的機関の注意喚起などを参考に、自分たちで書き直す |
| C-05 | **だます側のやり方は書かない。** 会話型でも、相手の発言は公的機関の注意喚起に書かれている範囲にとどめ、見抜き方と正しい行動に絞る |
| C-06 | **解説には必ず書く**：結末ごとに「何が起きたか」「どこで気づけたか（見るべき場所）」「正しい行動」、被害の結末では「被害にあったあとの対処」、シナリオに1つ以上の参考資料（公的機関の注意喚起など） |
| C-07 | **作った人とは別の人が確認してから公開する**（[8.2節](#82-シナリオの作成から公開まで)） |
| C-08 | 必要以上に怖がらせる表現や、特定の人を傷つける表現を使わない。被害の結末も、責める言い方にしない（「だれでもだまされうる」を前提に書く） |
| C-09 | **分岐の形の決まり**（[5.2節](#52-シナリオの組み立て)）を守る。取り込むときに自動でチェックし、守れていないシナリオは公開できない |

### 5.7 シナリオのデータ項目

画面はHTMLとして保存せず、項目ごとに保存して、形式ごとのテンプレートで組み立てる（XSS対策）。シナリオは YAML ファイルで書き、コマンドでDBに取り込む（[F-16](#f-16-シナリオの管理編集者管理者)）。

**シナリオ**

| 項目 | 必須 | 内容 |

| 導入 | ○ | 始める前に表示する状況（例：「あなたは20歳。ネット通販の荷物を待っている」） |
| 架空ブランド | | どのブランドをかたるか（またはどのブランドからの本物か） |
| 詐欺か本物か | ○ | |
| 手口のタグ | 詐欺なら○ | T01〜T15から1つ以上 |
| 詐欺の種類 | | 被害データと結び付ける区分 |
| 最初の場面 | ○ | |
| 参考資料 | ○ | 公的機関などの資料名とURL。1つ以上 |
| 初期の難易度・状態・作成者・確認者 | ○ | 確認者は作成者と別の人 |

**場面**

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| キー | ○ | シナリオの中で一意の名前（例：`sms_arrived`） |

| 振り返りの説明 | | この場面で見るべき場所と説明（振り返りで強調する） |

**操作（選択肢）**

| 項目 | 必須 | 内容 |

## 6. 機能要件

各機能の「確認方法」は、完成したかどうかを判断する条件（受け入れ条件）。自動テストか、手での操作で確かめる。

### F-01 アカウント

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| F-01-1 | 必須 | ユーザー名・パスワード・ニックネームで会員登録できる。メールアドレスと氏名は集めない | 登録後にログイン状態になる。同じユーザー名では登録できない |
| F-01-2 | 必須 | ログイン・ログアウトできる | 誤ったパスワードではログインできず、「ユーザー名またはパスワードが違います」と表示される |
| F-01-3 | 必須 | パスワードを変更できる | 変更後は新しいパスワードでだけログインできる |
| F-01-4 | 必須 | 年代を任意で登録できる（10代以下〜80代以上） | 未登録でもすべての機能を使える |
| F-01-5 | 必須 | 退会できる | 退会するとアカウントが削除され、プレイの記録は個人と結び付かない形で統計用に残る |
| F-01-6 | 必須 | ログインに続けて失敗すると、一定時間ログインできなくなる | 5回失敗すると15分間ログインできない |

### F-02 プレイ

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| F-02-1 | 必須 | ゲストでも会員でも、シナリオの一覧から1本選ぶか、「おまかせ」（3本）で始められる | トップ画面から2タップ以内で導入の画面が表示される |
| F-02-2 | 必須 | 導入を表示してから、最初の場面を表示する | 導入には状況と、「このシナリオは架空です」を表示する |
| F-02-3 | 必須 | 調べる操作をすると、物語は進まずに情報が表示される | 同じ場面にとどまり、調べた操作が記録される |
| F-02-4 | 必須 | 決める操作をすると、次の場面か結末に進む | 行き先はサーバーが決める。ブラウザにはシナリオの分岐の全体を送らない |
| F-02-5 | 必須 | 1本のプレイで、道筋（場面と操作の順番）と、場面ごとの考えた時間を記録する | 記録から道筋を再現できる |
| F-02-6 | 必須 | 結末に着くと、結末と振り返りを表示する（[F-04](#f-04-結末と振り返り)） | |
| F-02-7 | 必須 | おまかせの3本が終わると結果画面を表示する | 結末の評価、見つけた気づきの数、点数、会員ならレートの変化を表示する |
| F-02-8 | 必須 | 結果をニックネームで当日のランキングに載せるかどうかを選べる | 載せないを選ぶとランキングに表示されない |
| F-02-9 | 追加 | 60秒操作がないと「ヒント」ボタンが目立つ。押すと、その場面で調べるとよい場所を1つ示す | ヒントを使ったことが記録され、振り返りに表示される |
| F-02-10 | 余裕 | 途中でやめても、同じ端末なら続きから再開できる | 再開すると、最後の場面から始まる |

### F-03 仮想アプリと会話の再現

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| F-03-1 | 必須 | メールアプリ：受信トレイ（問題のメールのほか、ふつうのメールも並ぶ）、メール本文、差出人の詳細、リンクの長押し（PCではマウスを乗せる）でURLを表示、迷惑メールとして報告、削除、返信 | シナリオに登録した操作が、それぞれの置き場所に表示される |
| F-03-2 | 必須 | メッセージアプリ：SMSとSNSのダイレクトメッセージの画面。送信元の詳細、リンクの長押し、ブロック・報告、返信 | 同上 |
| F-03-3 | 必須 | ブラウザ：アドレスバー（押すとURL全体を表示）、ページ本体、入力欄、タブを閉じる | 同上 |
| F-03-4 | 必須 | ホーム画面：公式アプリ、ブックマーク付きのブラウザ、電話、家族とのチャットのアイコン。アプリ型のどの場面からでも開ける | シナリオに登録していない操作を押すと「このシナリオでは使いません」と表示し、記録しない |
| F-03-5 | 必須 | 会話型：相手の発言を1つずつ、入力中の表示のあとに表示する。返事は2〜4個の選択肢から選ぶ。電話の場面では通話中の表示と「電話を切る」ボタンを常に表示する | 発言の順番がシナリオのとおりになる |
| F-03-6 | 必須 | シナリオの中のURLはリンクにしない。仮想の電話は実際に発信しない | HTMLに外部のサイトへのリンクや `tel:` が出力されないことを自動テストで確かめる |
| F-03-7 | 必須 | スマホの縦画面で、横にスクロールせずに操作できる。PCでは画面の中央に仮想のスマホ（幅最大420px）を表示する | 幅360pxの画面で横スクロールが出ない |
| F-03-8 | 追加 | 会話の時間差表示をやめて、すぐに全部表示する設定 | 設定が端末に保存される |

### F-04 結末と振り返り

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| F-04-1 | 必須 | 結末の題名、評価（アイコン＋文字）、何が起きたかを表示する | 色だけでなく、アイコンと文字でも分かる |
| F-04-2 | 必須 | 道筋を順にたどり、決めた場面ごとに「ここで見るべきだった場所」を画面の上で強調して説明する | 道筋のすべての場面に、登録した振り返りの説明が表示される |
| F-04-3 | 必須 | 見つけた気づきと、見逃した気づきを一覧にする | 「見つけた気づき 2 / 3」のように表示する |
| F-04-4 | 必須 | 正しい行動、（被害・危ないの結末なら）被害にあったあとの対処、参考資料を表示する | 参考資料は新しいタブで開く公的機関などのページ |
| F-04-5 | 必須 | 振り返りの下に、相談先の案内へのリンクを表示する | 相談先のページ（[F-15](#f-15-案内ページ)）に移動できる |
| F-04-6 | 必須 | 振り返りから、フローチャート（[F-19](#f-19-分岐のフローチャート)）と実際の被害データ（[F-20](#f-20-実際の被害データ)）に進める | |

### F-05 レーティングとおまかせ

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| F-05-1 | 必須 | 1本終わるたびに、会員のレートとシナリオの難易度を、結末の点数で更新する（[10.1節](#101-レーティング)） | 計算例どおりの値になることを自動テストで確かめる |
| F-05-2 | 必須 | シナリオの難易度を★1〜5で表示する | 難易度の値と★の対応が10.1節のとおりになる |
| F-05-3 | 必須 | 会員のおまかせでは、ちょうどよい難しさのシナリオと、苦手な手口のシナリオを多めに選ぶ（[10.2節](#102-おまかせの選び方)） | 苦手な手口が分かっている会員で、3本中1本以上が苦手な手口になることを自動テストで確かめる |
| F-05-4 | 必須 | ゲストのおまかせでは、難易度と形式を混ぜて選ぶ | 3本の形式がすべて同じにならない |
| F-05-5 | 必須 | 同時にプレイしても、レートが壊れない | 同じシナリオへの同時の更新を再現した自動テストで、更新が失われないことを確かめる |
| F-05-6 | 必須 | レートと難易度の更新には、その人のそのシナリオの1本目の記録だけを使う | やり直しや2回目のプレイでは更新されない |

### F-06 履歴・苦手分析（保存）

| ID | 優先度 | 要件 | 確認方法 |
| --- | --- | --- | --- |

## 8. 主な処理の流れ

### 8.1 プレイと採点

```mermaid
sequenceDiagram
    actor U as 利用者
    participant V as 画面（Django＋htmx）
    participant E as シナリオの進行
    participant R as 採点・集計の処理
    participant DB as DB
    U->>V: シナリオを始める
    V->>E: プレイの記録を作る（1本目かどうかを判定）
    E-->>V: 最初の場面
    loop 結末に着くまで
        U->>V: 操作する（調べる／決める）
        V->>E: 操作を送る
        E->>DB: 道筋に1行追加（場面・操作・考えた時間）
        E-->>V: 調べた結果、または次の場面
    end
    E->>R: 結末に着いた
    R->>DB: 1本目なら、シナリオの難易度と会員のレートを読む（更新が終わるまで他の更新を待たせる）
    R->>R: 結末の点数で、レートと難易度を更新
    R->>DB: 結末と、更新前後のレート・難易度を保存
    R-->>V: 結末、振り返り
    V-->>U: 結末と振り返りの画面を表示
```

- 次の場面はサーバーが決める。ブラウザにはシナリオの分岐の全体を送らない（ネタバレと、記録の改ざんを防ぐ）。
- 送られた操作が、その場面に登録された操作でないときは受け付けない。

### 8.2 シナリオの作成から公開まで

```mermaid
stateDiagram-v2
    state "YAMLで書く" as yaml
    state "下書き" as draft
    state "確認待ち" as review
    state "公開" as published
    state "非公開" as hidden
    [*] --> yaml
    yaml --> draft : 取り込み（分岐とルールの自動チェックを通る）
    yaml --> yaml : チェックのエラーを直す
    draft --> review : 作成者が確認を依頼
    review --> published : 別の編集者がプレビューで全場面を確かめて公開

```

シナリオのYAMLは Git で管理し、作成者と確認者のやり取りは GitHub の Pull Request で行ってもよい。

### 8.3 投稿の審査

1. 会員が怪しいメッセージを文字で投稿する（電話番号・メールアドレスらしい文字列は自動で伏せ字になる）。
2. 編集者が内容を確かめ、「採用」か「見送り」を決めて理由を記録する。
3. 採用した投稿は、作成のルール（5.6節）に沿って架空ブランドに置き換え、シナリオの素材にする。投稿そのものは公開しない。

## 10. アルゴリズムの要件

### 10.1 レーティング

教育向けのシステムで使われている方法（Pelánek, 2016）にならい、1本のプレイを「人とシナリオの対戦」とみなしてイロレーティングで計算する。結果 R は、結末の点数（[5.3節](#53-結末の評価)）を使う。

```
予想の点数    P = 1 / (1 + 10^((D − S) / 400))     S：人のレート、D：シナリオの難易度
人のレート    S' = S + K人 × (R − P)              R：結末の点数（最善1.0、安全0.7、危ない0.3、被害0）
シナリオの難易度 D' = D − Kシ × (R − P)
```

| 項目 | 初期値（運用しながら調整する） |
| --- | --- |
| 人のレートの初期値 | 1500 |
| シナリオの難易度の初期値 | やさしい 1300、ふつう 1500、むずかしい 1700 |
| K人 | 32 |
| Kシ | 1本目の記録が30件になるまでは32、それ以降は16 |
| ゲストのプレイ | 人のレートを1500とみなし、シナリオの難易度だけを K=8 で更新する |
| 難易度の★ | 1350未満 ★1、1450未満 ★2、1550未満 ★3、1650未満 ★4、1650以上 ★5 |

計算例：レート1500の人が難易度1700のシナリオで最善の結末になると、P≒0.24、人のレートは＋24.3、シナリオの難易度は−24.3（K=32の場合）。同じ条件で安全の結末なら、R−P≒0.46 で、人のレートは＋14.7。

**おまかせの点数（当日のランキング用）**：1本ごとに、結末（最善100・安全70・危ない30・被害0）＋見つけた気づき1つにつき10点（1本30点まで）。3本の合計（最大390点）。

### 10.2 おまかせの選び方

**会員（3本）**

1. 候補は、公開中のシナリオから、その人がまだ遊んでいないもの（すべて遊んだら、最後に遊んでから7日以上たったもの）。
2. 各シナリオの予想の点数 P を計算し、P が0.6〜0.75に近いシナリオを優先する（簡単すぎず、難しすぎない）。
3. 苦手な手口（安全以上の率が低い上位2つ）のシナリオを、3本中1本以上入れる。
4. 3本の形式がすべて同じにならないようにする。詐欺と本物は、3本がすべて本物にならないようにする。
5. 条件を満たすシナリオが足りないときは、条件を順に緩めて補う。

**ゲスト（3本）**：難易度を混ぜ（★1〜2、★3、★4〜5 から1本ずつ）、形式を混ぜる。**展示会（1本）**：2〜3分で終わるシナリオから、当日のプレイ数が少ないものを優先する（フローチャートの割合を偏りなく集めるため）。

**テストのために**：乱数の種（シード）を外から渡せるようにして、自動テストで同じ選び方を再現できるようにする。

### 10.3 URLの解析

URLの読み方トレーニング（F-14）と、シナリオの中でリンクを長押ししたときの表示に使う。**実在のURLが安全かどうかを判定する機能ではない。**

1. **部品に分ける**：スキーム、ユーザー情報（`@` の前の部分）、ホスト名、ポート、パス、クエリ。
2. **登録ドメインを求める**：Public Suffix List（ドメインの区切りの公開リスト）を同梱し、ネットにつながなくても計算できるようにする。
3. **国際化ドメインを戻す**：`xn--` で始まる表記（Punycode）を元の文字に戻して並べて表示する。
4. **紛らわしい文字を見つける**：Unicode が公開している「見た目が紛らわしい文字」のデータ（UTS #39）を使い、架空ブランドの公式ドメインと見た目がそっくりなドメインを見つける。複数の文字体系が混ざったドメインも見つける。
5. **よくある見せかけを見つける**：公式の名前がサブドメインに入っているだけのもの（`kotori-bank.example.login-check.test`）や、`@` の前に公式の名前を置いたものなど。

### 10.4 文字の無害化

- 利用者が書いた文字（コメント・投稿）の中のURLは、リンクにせず、`hxxps://example[.]com` の形で表示する。
- 投稿の中の電話番号・メールアドレスらしい文字列は、保存する前に伏せ字にする。
- 画面に出す文字は、すべてテンプレートのエスケープを通す。

### 10.5 集計のルール

- フローチャートの割合（F-19）、落とし穴ランキング（F-13-2）、年代別の結末（F-13-4）、レートと難易度の更新は、**各人の1本目の記録**（is_first かつ is_retry でない、今の版の記録）だけを使う。2回目以降は結末を知っているため、最初の反応が分からなくなる。
- 学習効果（F-13-7）は、1本目と2本目以降を比べる。
- 年代別などの区分は、人数が5人未満なら表示しない。挑戦状と展示会のニックネームの表示（F-19-4）を除き、個人が分かる形では表示しない。
- 展示会の集計は、展示会の日付で区切る。
- 統計には、公開中のシナリオの記録だけを使う。プレビューの記録は残さない。

### 10.6 フローチャートの配置

外部のライブラリを使わず、サーバーで座標を計算して SVG で描く（ネットにつながなくても動く。N-03、N-04）。

1. **段を決める**：最初の場面を0段目とし、各場面の段を「最初の場面からの最も長い道のりの手数」にする（ループがないので必ず決まる）。結末はすべて最下段に置く。
2. **段の中の並び**：親の場面の並び順の平均で並べ替える（重心法）。これを上下に2〜3回繰り返し、矢印の交差を減らす。
3. **大きさ**：箱の幅と段の高さを決め、全体が収まる大きさを計算する。スマホでは拡大・移動できる枠に入れる。
4. **重ねる情報**：自分の道筋（太線・色）、矢印ごとの選んだ割合（矢印の太さにも反映）、結末ごとの到達した割合、伏せる場面（「？」）。
5. **テスト**：配置の計算は、決まった入力に対して同じ座標を返すことを自動テストで確かめる。

### 10.7 シナリオの検証

取り込み（F-16-1）とフォームでの編集（F-16-8）のたびに、次をすべて確かめる。1つでも満たさなければ保存しない。

| チェック | 内容 |
| --- | --- |
| 行き先 | 決める操作は、同じシナリオの場面か結末のどちらか1つだけを指す。調べる操作は行き先を持たない |
| ループがない | 場面と決める操作をたどったとき、同じ場面に戻らない |
| たどり着ける | すべての場面と結末に、最初の場面からたどり着ける |
| 行き止まりがない | すべての場面から、いずれかの結末にたどり着ける。決める操作のない場面はない |
| 長さ | 最初の場面から結末までの決める回数が、どの道筋でも1〜5回。結末は3〜5個 |
| 結末 | 最善の結末が1つ以上ある。被害・危ないの結末には aftercare がある |
| 気づき | 詐欺のシナリオには、気づき（is_clue）が1つ以上ある |
| 作成のルール | URLのドメインが予約済み（`.example`・`.test` など）、電話番号が伏せ字（相談窓口の番号を除く）、架空ブランドが一覧にある |

### 10.8 被害データとアプリのデータの比較

1. **実際の構成比**：詐欺の種類と区分（例：年代）ごとに、各カテゴリの件数 ÷ 区分の合計。合計は、登録した値の合計を使う（グラフに数値がない区分は入れていないので、出典の総数とは合わないことがある。その旨を注意書きに書く）。
2. **アプリの率**：同じ詐欺の種類のシナリオの1本目の記録で、年代ごとに「被害の結末になった人数 ÷ 遊んだ人数」。
3. **並べ方**：年代を横軸にして、実際の構成比（棒）とアプリの率（折れ線）を2つの軸で表示する。意味が違う数字なので、凡例と注意書きで区別する。
4. **年代の区分**：被害データの区分（10代以下〜80代以上）に、プロフィールの年代の区分を合わせる。

## 13. 外部とのやり取り

- **外部API**：使わない。被害データは、管理者が出典を確かめて手で登録する。

| API | 内容 | 利用者 |
| --- | --- | --- |
| 統計 | 手口別・形式別・年代別の結末の集計、落とし穴ランキング、調べた人と調べなかった人の比較 | 全員（集計結果のみ） |
